### 1.5 通道口分组

D1 的 9 组（`data/b-building.js:64-72`）与 xidian 源 `handoff/ref0g/script.js` 的 `entrance` 对象**键集合完全相同**（1、6、8、23、45、71、72、91、92），逐组比对后**只有 1 处不同**：`groups[45]` 比源多一个 508（16 条 vs 源 15 条），其余 8 组完全一致（仅类型 number vs string）。

分组质量（实测）：79 条成员关系、79 间教室、每间恰好属于 1 组 → **正分区**，无跨组重复、无遗漏。这比房间清单可靠，可作"入口提示"的 canonical 字段。但注意：

- 分组只说明"从哪个通道口近"，**不含 8 个导航入口与 9 个通道口的对应关系**，两套数据无法 programmatic join（D2 没有 group 字段，D1 没有 node/edge）。
- `app/b-building.js:21-27` 的 `groupForRoom` 取"第一个命中的组"，若将来出现跨组房间会静默取错，建议测试里加正分区断言（§5.3）。

## 2. D1 的「79 间 / 7 层」与两个上游清单是否一致

数据源与实测方法：BMap seed 取 `handoff/bmap/BMap-master/docker/initdb/03-seed-data.sql` 的 `room` 表；xidian 取 `handoff/ref0g/script.js` 的 `buildingData`；D1 取 `data/b-building.js`。

### 2.2 关键结论

- **D1 不是任何单一上游的拷贝，而是"逐层并集"**：seed 77 ∪ {215} ∪ {508} = 79；xidian 78 ∪ {509} = 79。逐层验证 F1 4 / F2 9 / F3 12 / F4 21 / F5 20 / F6 9 / F7 4，全部吻合（脚本实测）。所以 D1 的 79 是"可解释的 79"，不是随便多出来的。
- **「BMap 78 间」是错的**：`03-seed-data.sql:573` 写 `-- 5. room (78 条)`，但逐层行数为 4+8+12+16+5+14+5+9+4 = **77**；第 584 行注释"Floor 2 (9 间)"而其下只有 8 行。缺口正是 **215**（seed 的 F2 节点也跳过了 posX=70 的位置：B211 在 60、B216 在 80，见 `:48-58`）。D1 头部注释沿用"78 间教室拓扑"（`data/b-building.js:3`）属于以讹传讹。
- **xidian 的 78 也不等于真值**：4 层 `422` 出现两次（源 22 条、去重 21），5 层把 509 写成了 508（图上是 509，见 §4）。"78" 恰好与 seed 自称的 78 相同，纯属巧合，不能互为佐证。
- **缺**：D1 少 321、324（D2 有，且 3F 图上可见）、少 325（两套都没有，图上可见）；seed 少 215、508。
- **多**：D1 多 508（图上看不到，见 §4.3，疑为 509 误写）；相对 seed 多 215。
- **重**：D1 无重号；上游 xidian 有 422 重复；D2 有 **8 条重复边**（非房间，见 §3.4）。

## 3. D2 的 routes / validation 能否作为「入口→教室」权威数据

### 3.1 我做的独立复算（不依赖其 validation 字段）

用 D2 的 `edges` 重建邻接表，以 `time` 为权重跑 Dijkstra：

- **8 个入口 × 80 间教室，全部可达**（每个入口都是 80/80，无不可达教室）；最短 8.0 s，各入口最远分别为 ENT1 276.6 / ENT2 289.7 / ENT3 228.1 / ENT4 193.2 / ENT5 169.4 / ENT6 178.8 / ENT_NE 201.2 / ENT_NW 176.1 s。
- **7 条 routes 的 time 与我的最短路径逐条完全相等**（如 ENT1→F7_707 = 276.6、ENT1→F2_215 = 95.7），路径节点序列的相邻跳都能在 `edges` 中找到对应边（0 处断链）。说明 routes 是用 Dijkstra 真算出来的，不是手填。
- `validation.reachableFromENT1 = 130` 与 `nodes.length = 130` 一致；`missingRooms`/`missingEntrances` 为空数组；`entrancesWithUnreachableRooms = {}`，我的复算确认这条**确实成立**。

### 3.2 可以作权威的部分

1. **拓扑连通性**：8 入口 × 80 教室全通，无孤立节点（130 节点度数均 > 0）。这层结论可信。
2. **节点/边/竖井的完整性**：130 = 80 房间 + 29 楼梯 + 13 电梯 + 8 入口；167 条边端点全部存在、无自环；`stairs[].node/attach`、`elevators[]`、`entrances[]` 引用的节点全部存在（0 处悬空）。
3. **房间 ↔ 节点一致性**：80 条 `rooms[].node` 与 `nodes` 的 x/z/level/wing **0 处不一致**，可直接用于"教室 id → 图节点"翻译。
4. **路线示例**：7 条可作为 UI 演示用例（时间可复现到 0.1 s）。

### 3.3 不能作权威的部分（含它自认的限制）

**它自称的置信度与估算限制**（原文出处）：

- `meta.confidence = "schematic-estimated"`（`assets/b-building-data.js:30`）；`B_DATA_REPORT.md:4` 写"可导航优先的简化拓扑，不是实测几何；尺寸/坐标标注为估算"。
- 尺寸 270 m × 19–40 m × 40 m、层高 5.71 m = 40/7 为估算（`meta.dimensions`、`meta.notes[1]`）。
- "教室沿走廊按 15.6 m 柱距铺开（总长 270 m），**不是平面图像素坐标**"（`notes[0]`、报告 §4）。实测确实如此：同层相邻房间 x 间距恒为 15.60 m，房间共用同一批 x（如 25.6/41.2/56.9…），与图上的房间宽度无关。
- "楼梯 20 s/层、电梯 12 s/层（含平均等待）"（`notes[1]`、`gen_b_data.py:23-24`）——常数拍定，非实测。
- "北楼 4/5 层用 z=-30 偏移，坡道/楼层差用 passage 边简化"（`notes[2]`）；报告 §4 进一步自认"'北楼层数为负一'的标高关系**未精确建模**"。实测：北楼与南楼只有 **2 条 passage 边**（`N4_443↔F4_421`、`N4_434↔F4_411`，30 s），北楼内部竖向靠 2 条楼梯边（`N4_443↔N5_537`、`N4_434↔N5_529`）。
- "321/324 仅平面图可见，置信度低；107考/215值 作为别名"（`notes[3]`）。实测房间置信度 `medium 78 / low 2`（low = 321、324），`source` 为 `blog+floorplan 78 / floorplan-only 2`；但 **215 被标成 `medium`**，而它同样只在 xidian 的 JS 清单里出现、图上没有（§4.3）——置信度标注前后不一致。
- "8 个入口（6 南 + 2 北），GPS 从 BMap 16 个物理入口中近似选取"（`notes[4]`）；报告 §4 还写"入口与 16 物理入口的对应为近似映射；精确对应需现场核对"。
- 未建模对象清单：卫生间、办公室、配电室、值班室、开水器、消防箱、地弹门、多媒体总控室（报告 §4）。
- 入口置信度 8/8 为 `approx`（`assets/b-building-data.js` entrances[].confidence）。

**我复核出的额外问题**：

| 问题 | 证据 | 影响 |
|---|---|---|
| 8 条**重复边**，edgeCount 虚高 | 167 条中唯一 159 条；重复项正是北楼两条链：`N4_442-443 / 443-437 / 437-434 / 434-433`、`N5_538-537 / 537-532 / 532-529 / 529-528`，每条 30 m/24 s 各出现 2 次 | 生成器重复加边：`gen_b_data.py:221-234` 的全楼层循环已包含 N4/N5，`:252-259` 又单独建了一遍北楼链。Dijkstra 结果不受影响，但 `meta.edgeCount=167` 不是唯一边数，校验口径失真 |
| validation 只对 ENT1 下结论 | `gen_b_data.py:317-319` 用 `reachable("ENT1")` 算 `missingRooms`/`missingEntrances`；`reachableFromENT1` 字面也只是"从 ENT1 可达的节点数" | 字段名容易让人误以为"每个入口都查过"。全入口检查只体现在 `entrancesWithUnreachableRooms`（为空） |
| 入口起点不在首层 | ENT3@F2、ENT4/5/6@F3（§1.4） | 这些入口的耗时与 ENT1/2 不可比，不能横向排名 |
| routes 只覆盖 4/8 入口 | 起点集合 = ENT1×4、ENT3、ENT6、ENT_NW；**ENT2、ENT4、ENT5 一条样例都没有** | 不能作为"每入口都有路径"的证据 |
| 无距离、无换层数、无置信度字段 | routes[] 仅 `name/from/to/found/path/time` | 页面无法展示"步行 X 米 / 上下 Y 层" |

**结论**：`assets/b-building-data.js` 的 **拓扑（nodes/edges/entrances/attach）可以作为"入口→教室"路径的权威数据**——连通性与路径时间可复现、可校验；但**时间/坐标/入口楼层属于示意估算**，只能作为演示值，不能对外称"实测步行时间"。若 B 页要展示耗时，应同时展示 `confidence: schematic-estimated` 与"估算"字样，或只显示"经 X 号通道口、上 Y 层"这类拓扑结论。

### 3.4 routes/validation 作为"权威"的前置修复项

1. 去重北楼 8 条边（或在生成器里删掉 `:252-259`），并把 `meta.edgeCount` 改为唯一边数。
2. 为 ENT2、ENT4、ENT5 各补至少 1 条样例，使 8/8 入口都有可复现路线。
3. validation 增补：`checkedEntrances[]`、`uniqueEdgeCount`、`duplicateEdges[]`、`roomsWithoutSampleRoute[]`。
4. 若要给"入口→教室"整体结论，直接预生成 8×80 的距离/耗时表（静态 JSON，约 640 行），避免前端重复跑 Dijkstra，也便于测试逐格断言。

## 5. 建议（不引入后端/框架）

### 5.1 B 页的 canonical 选型

**建议：数据层以 `assets/b-building-data.js` 为唯一 canonical；`data/b-building.js` 降级为"图纸页投影"。**

理由（按证据）：

1. D2 有生成脚本（`tools/gen_b_data.py`）、版本号、逐房间置信度、校验块，且 `3d.html:101` 已依赖它——**两页已经在用两套数据**，再维持"两套都权威"必然继续漂移（现状：79 vs 80）。
2. D1 独有价值只有三样：**楼层图路径、9 个通道口分组、16 个物理入口 GPS**。这三样都适合作为"投影字段"从 canonical 生成，不需要独立维护房间清单。
3. D2 缺的正是 D1 的这些字段，合并方向应是"给 D2 补 image/groups/physicalNumber"，而不是"给 D1 补图/边/路线"（后者等于重写生成器）。

落地方式（不改框架，纯静态）：

- 在 `gen_b_data.py` 末尾同时输出 `data/b-building.js` 投影：`{floors:[{id,label,image,rooms:[ids]}], groups, entrances(16 GPS)}`，房间数取下面"定案建议"里的口径。这样两页永远同源，`b-building.html` 与 `3d.html` 的房间数不再打架。
- 若本次不改代码：至少在两个文件头互标 `canonical: "assets/b-building-data.js"` / `derivedFrom`，并在测试中断言两文件房间集合相等（§5.3），让差异在 CI 里暴露而不是靠人读。

**房间清单定案建议**：给两条口径，二选一并写死，不要两页各用一套。

- **口径 A（推荐，含置信标注）81 间** = seed 77 + 215 + 321 + 324 + 325。321/324/325 有 3F 图证据（§4.2）；215 只有 xidian JS，标 `plan-unverified`；**508 不入库**，记为 509 的别名（理由见 §4.3）。
- **口径 B（只收有图纸证据的）80 间** = seed 77 + 321 + 324 + 325（215、508 都剔除）。

两条口径的差集恰好是 {215}，可先用 `status` 字段区分而不必二选一：seed 的 77 间全部能在 1–7 层图上找到（含北楼 5+5 在北四楼/北五楼带内），是本数据里唯一"全图可验"的基线。

### 5.2 需要补齐的字段（全部静态，无后端）

| 对象 | 建议字段 | 解决什么问题 |
|---|---|---|
| room | `wing`（S/N）、`level`、`node`、`aliases`（107考、215值、508→509）、`status`（`confirmed`/`plan-only`/`plan-unverified`）、`plan:{image, x, y}`（归一化 0–1 标注点） | 北楼归属、别名检索、置信度可展示、点击图上定位 |
| floor | `image`（现 D2 全无）、`wing`、`level`、`elevation`、`displayY`、`roomIds[]` | 两页共用一份楼层定义 |
| entrance | `physicalNumber`（BMap 1–16）、`navId`、`wing`、`groundLevel`（真实地面层，区别于 attach 层）、`attachNode`、`groupId`、`photo`（BMap 已有 16 张 `EntrancePicture/*.jpg`）、`confidence` | 解决"16 vs 8"的对应、编号同号不同物、入口照片展示 |
| group（通道口） | `id`、`label`、`rooms[]`、`entranceIds[]`、`source` | 把 D1 的分组与 D2 的 8 入口接上，才谈得上"从入口到教室" |
| route | `from`、`to`、`path`、`time`、`distance`、`floorsCrossed`、`confidence`；或改为运行时用 `edges` 现算，只保留 7 条样例 | 页面能显示"步行 / 换层"，并避免样例被当成全量 |
| validation | `uniqueEdgeCount`、`duplicateEdges[]`、`checkedEntrances[]`、`roomsWithoutPlanLabel[]`、`planOnlyRooms[]`、`roomsWithoutGroup[]`、`entrancesWithoutRoute[]` | 把 §3.3/§3.4 的问题变成可断言的字段 |
| meta（两文件） | `license:"NOASSERTION / course-demo-only"`、`sources[].license`、`version`、`generatedAt`、`upstreamCommit` | 目前两套数据都无 license 字段，只有注释与页脚一句"无 license" |

另外把 D1 头部注释里的"78 间教室拓扑"改成"77 间 room 表（seed 注释误写 78）"，避免审计结论被注释带偏。

### 5.3 建议新增的校验（可复用现有 `tests/run.js`，零依赖）

`tests/b-building.test.js` 现在只断言 7 层 / 16 入口 / 9 组 / `rooms > 70` / 图片存在（`:25-30`），强度不足。建议加（纯 `fs` + `vm`，与现有写法一致）：

1. 两文件房间集合**完全相等**（或按 §5.1 定案口径相等），否则 FAIL 并打印差集。
2. 每组 `rooms ⊆ floors 房间集`，且 9 组并集 = 全集、无跨组重复（保护现在的正分区）。
3. D2：边端点存在、**无重复边**（现在会 FAIL 8 条，正好暴露 `gen_b_data.py:252-259` 的 bug）。
4. D2：8 入口 × 80 教室全可达；7 条 route 的 `time` 等于重算 Dijkstra（误差 ≤ 0.1 s）。
5. 图源存在且 sha256 等于 `handoff/ref0g/1.jpg..7.jpg`（防止误换图/改图）。
6. `meta.roomCount/nodeCount/edgeCount` 与数组实际长度一致，`edgeCount` 用唯一边数。

### 5.4 不建议做的事

- **不要引入后端/数据库/框架**：现有静态 JS + Leaflet + three 已足够；缺口是字段与口径，不是服务端能力。
- 不要为"精确坐标"去接 CAD/BIM 或在线瓦片：本数据自认示意，课程演示没有必要，也会重新引入 license 风险。
- 不要在运行时前端做"双数据源合并"：会掩盖 79/80 的差异，且两套 id 体系（`"4"` vs `"F4"/"N4"`）不同，合并逻辑比生成一份数据更贵。
- 不要把 16 个物理入口直接当导航起点：其中 8 个未接入室内拓扑，另外多个同侧入口名称重复，选错也没有提示。
